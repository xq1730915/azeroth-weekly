# 艾泽拉斯周计划：第一版设计

日期：2026-10-25（Asia/Shanghai）  
适用游戏：魔兽世界国服正式服  
状态：用户于 2026-10-25 回复“继续”，书面设计已确认；进入开发计划阶段。

## 1. 产品目标与已确认需求

为同一个战网账号下四个 WoW 子账号的角色设置每周目标，统一查看宏伟宝库、手动制定的团本 BOSS 周计划，以及额外拾取币的持有、获取、使用和奖励记录。

必须遵守的产品规则：

1. 四个子账号只影响导入和数据归属。正常业务页面统一展示角色，不分组、不筛选、不标注子账号。
2. 团本周计划由用户手动选择角色、团本、难度和 BOSS。同步不能添加计划，也不能自动展开完整 BOSS 列表。
3. 团本页面只显示当前所选周的计划 BOSS。用于添加计划的选择器可以显示对应版本的完整 BOSS 目录。
4. 宏伟宝库按游戏实际有效活动统计，包括计划之外的活动。
5. ROLL 币指额外拾取币，不是需求／贪婪投骰。记录余额、获取、消耗、关联活动和获得的奖励。
6. 同步数据必须显示实际采集时间。未知、过期和零进度是不同状态。

## 2. 交付形态与范围

采用 Windows 桌面软件配合游戏 Lua 插件。数据保存在本机，无需战网密码或云端登录。

第一版包含：统一角色总览、宝库目标、BOSS 计划编辑与批量复制、逐 BOSS 进度、额外拾取币账本、四个来源的数据导入、每周历史归档、本地备份与恢复。

第一版不包含手机云同步、公会分装备、团员投骰排名、自动操作游戏和其他周常任务管理。插件用于读取游戏开放的数据和记录事件。

此前比较过纯插件、桌面端配合插件、网页配合同步助手三种方式。桌面端配合插件可以同时处理四个本机数据来源，并提供统一的角色视图，因此作为第一版方案。

## 3. 页面与主要流程

### 3.1 统一总览

顶部提供周选择、重置倒计时、角色搜索、只看未达标和同步状态。主区域每行一个角色，包含角色名、服务器、职业、宝库目标进度、计划 BOSS 完成数量、持币余额和采集时间。

子账号信息不出现在角色行、角色详情、筛选器或排序选项中。姓名相同的角色通过服务器区分；仍重名时允许添加显示备注。身份归属始终使用内部 ID，不能使用显示名称。

点击角色打开其宝库、BOSS 计划和币账本。没有计划时显示“本周还没有 BOSS 计划”和添加入口，不显示所有未击杀首领。

### 3.2 宏伟宝库

展示客户端当前版本支持的各活动类别及奖励栏位，不硬编码某一赛季的类别、次数和奖励等级。每个栏位显示采集到的当前进度、解锁门槛、奖励等级和达标状态。

用户为角色选择需要达到的栏位及最低奖励等级；允许只选栏位而不限制奖励等级。目标达标要求该栏位已解锁，且已设置的最低等级条件得到满足。无法确认等级时标为待确认。

当前周的活动积累与上一奖励周期的待领奖状态分别显示。领取上一周奖励不能将本周进度清零，也不能使本周目标自动达标。宝库仅展示可选奖励，不将多个已解锁栏位解释为可同时领取多件装备。

宝库总览使用“已达成目标栏位／已设置目标栏位”，没有目标时显示“未设置”。进度未知的目标显示待同步，并计入待确认数量，不标成未完成或已完成。

### 3.3 BOSS 计划

添加流程：选择一个或多个角色 → 选择团本 → 选择难度 → 勾选 BOSS → 可选目标装备和用币意向 → 保存。

同一角色、同一周、同一团本、同一难度和同一 BOSS 只能有一个计划项。同一 BOSS 的不同难度可以分别加入计划。

计划列表列：角色、团本／BOSS、难度、本周击杀、拾取资格、目标装备、计划用币、实际用币、奖励。这里的用币意向是计划字段，不占用或扣除真实余额。

拾取资格只有在客户端提供可靠结果时显示“可用／已用”；否则显示“未知”。不能仅依据一次击杀事件推断资格或进度锁定规则。

同步导入所有可用活动事实，但只有与手动计划键匹配的 BOSS 才出现在计划列表。用户在击杀后加入该 BOSS，只要已有可靠的当周记录，就可以立即匹配完成情况。

删除计划仅删除展示和目标关系，不删除击杀事实或币流水。编辑目标装备和用币意向不会改变历史奖励记录。

提供“复制上周计划”和“应用到所选角色”。复制只复制目标，不复制完成状态、实际用币或奖励；遇到相同计划项跳过并显示新增与跳过数量。第一版新周由用户主动复制或新建，不自动新增 BOSS。

### 3.4 ROLL 币账本

角色摘要显示：最近可靠余额、本周已记录获取、本周已记录消耗，以及流水覆盖起点。只覆盖部分时段时，明确标注“已记录”，不能将其称为完整游戏历史。

流水字段：事件 ID、角色、时间、赛季、获取／消耗／调整、数量、获取来源或使用活动、团本、难度、BOSS、拾取专精、奖励物品链接、物品等级、自动／手动来源和确认状态。

余额快照与流水是两类数据。首次导入有余额而没有历史流水时，将它保存为余额基准，不凭空生成获取或消耗记录。只有余额变化却无法确定原因时，标记差异待核对，不猜测 BOSS 或奖励。

自动记录只接受能够可靠关联的游戏数据；不完整事件保留为待核对。允许手动补录或修正说明，显示来源。手动流水默认不覆盖已采集余额；没有可靠游戏余额时可另设明确标注的手动余额基准。

账本展示角色全部已记录获取和消耗，包括计划之外的 BOSS、地下城等活动。团本计划页面仍只显示计划 BOSS。这是账本完整性与计划可见性的区别。

### 3.5 同步与设置

首次设置选择国服正式服安装目录，检查插件位置和可读取的数据文件。识别到的数据来源可在技术性的导入管理页中选择和检查；来源不进入日常角色界面。

兼容四个子账号对应不同存档目录，以及多个角色数据集中在同一个可读取文件的情况。不能假定“四个子账号必然对应四份文件”。绑定依据实际扫描结果和插件提供的身份信息。

自动监听数据文件变化，并提供“立即读取”和手动选择插件存档文件的入口。点击读取不能强制游戏把内存中的新数据写入磁盘；没有新存档时保留原采集时间并提示在游戏中切换角色、正常退出或执行 /reload。

支持 JSON 备份与恢复，包含计划、角色映射、游戏事实、流水和规则版本；CSV 只用于导出查看账本。恢复前自动备份现有数据库。第一版不提供跨备份文件自动合并。

## 4. 周期、完成率与历史

以游戏服务器时间和重置接口提供的重置时点识别国服游戏周，界面时间使用 Asia/Shanghai。游戏周不能直接使用自然周或电脑本地星期。

在有最新服务器时间和重置数据时生成已确认周标识；离线时沿用最近可靠时间推算并标记状态。遇到维护调整，以新采集到的重置信息校正，保留已有历史关联。

新周启用后：旧计划和快照可回看；新周不会继承击杀或宝库完成状态；未登录或未重新采集的角色显示待同步。币余额是跨周持有量，不因周重置而清零；赛季转换由游戏余额及相应规则决定。

BOSS 完成率＝已确认击杀的计划项／当前周计划项总数。同步未知项同时显示“待确认 N 项”，不会当作已完成。没有计划时显示未设置，不显示 100%。

宝库与 BOSS 使用各自完成率，不把解锁栏位数、击杀数和币数量相加为一个总分。币使用属于记录，除非用户设置对应计划，否则不视为应完成的周目标。

历史明确区分游戏采集时刻、桌面导入时刻和手动记录时刻。无法完整采集的旧周标注数据不完整，不能用后续周快照补成完整旧周数据。

## 5. 数据架构与四来源合并

建议使用 Tauri 2 桌面外壳、React／TypeScript 界面、Rust 本地导入模块、SQLite 数据库与 Lua 游戏插件。前端通过明确的本地命令读取及修改业务数据，不能自行拼接路径读取任意文件。

核心记录：

| 记录 | 作用与关键约束 |
| --- | --- |
| ImportSource | 来源 ID、路径、客户端分支、最后成功导入和文件摘要；仅导入模块使用 |
| Character | 内部 ID、地区、角色 GUID、服务器、姓名、职业、显示备注 |
| CharacterSource | 关联角色与一个或多个导入来源，避免将同一角色拆成多个角色 |
| GameWeek | 地区、游戏周起止时间、确认状态及时间依据 |
| VaultTarget / VaultSnapshot | 用户目标与游戏实际栏位进度分开，关联角色、周和活动栏位 |
| BossPlan | 角色、周、团本、难度、首领 ID、装备目标、用币意向；组合键唯一 |
| EncounterObservation | 角色、周、难度、首领、采集时间、击杀与拾取资格证据 |
| CurrencySnapshot | 角色、币种、赛季、采集时间和游戏余额 |
| CurrencyEvent | 逐笔获取／消耗／调整、数量、来源活动、奖励、证据和导入去重标识 |
| ContentRules | 客户端版本、赛季、团本／首领目录、币种与规则版本 |

插件优先使用国服正式服内可获取的角色 GUID 作为身份依据，结合地区和客户端分支确定角色；来源路径用于追踪，不用于界面分组。同一 GUID 的重复快照合并为同一角色。

旧文件缺少可靠身份信息时进入待匹配队列，不根据“姓名相同”静默合并。改名或转服只能在身份依据可确认时自动迁移，不能以显示名称强行推断。

同一份文件重复导入不重复创建角色、击杀记录或用币流水。快照按采集时间处理，旧快照不能覆盖新快照。文件包含更早但尚未导入的明确事件时，可追加该事件。

导入事件优先使用插件持久化的事件 ID，并结合来源身份和角色做去重。跨文件重复事件只在有可靠同一事件标识时合并；仅凭相同时间、数量和奖励不能直接删除看似重复的不同事件。

## 6. 组件边界与数据流

1. 游戏采集插件：读取客户端开放数据、监听可用事件、记录角色身份、保存完整快照和持久事件；不持有桌面计划的权威副本。
2. 来源扫描与文件读取：发现存档，等待文件写入稳定，生成只读副本；不修改游戏存档。
3. 数据解析与校验：将 SavedVariables 的受限数据结构转换为带版本的内部格式，不执行导入文件中的 Lua 代码；限制文件体积、嵌套深度和字段类型。
4. 导入与身份合并：校验记录、去重、关联角色和游戏周，通过事务写入数据库。
5. 进度服务：根据用户目标和游戏事实生成宝库及 BOSS 视图；不能从采集事实创建用户计划。
6. 桌面界面：统一角色视图、计划编辑、账本核对、历史查看与导入诊断。

主流程：游戏内活动 → 插件内存记录 → 游戏保存 SavedVariables → 桌面监听变化 → 解析／校验 → 事务导入 → 匹配手动计划 → 更新视图。

版本和赛季内容由采集数据及随软件发布的规则包提供。首领名称、图标和活动类别优先使用游戏提供的本地化信息；规则包使用稳定 ID 关联，不将中文名称作为主键。游戏更新不等于所有新增机制都能自动适配，未支持的字段显示不可用并提示适配状态。

## 7. 同步能力边界与错误处理

客户端当前源码可以确认存在宝库活动、奖励周期和周重置相关接口。它们是采集依据，仍需在用户实际国服客户端验证返回结果和权限。

额外拾取事件是否包含可靠的 BOSS、消耗数量和奖励关联，需要先完成采集验证。第一版交付策略固定为：可确认的事件自动写入，缺字段事件待核对，安装前不能可靠还原的历史由用户补录。若无法可靠采集逐笔记录，余额同步加手动流水仍作为可用功能交付，并明确显示覆盖能力。

同理，普通拾取历史不能当作额外拾取历史。物品进入背包、币减少、附近有首领等独立信号不能单独证明一次额外拾取的因果关联。

文件读取中、写入未结束或解析失败时，保留最后成功数据，显示来源异常并允许重试。未选来源不会导致其他来源的数据清空。批次校验通过后用事务写入；失败回滚整个批次，避免部分角色刷新而其他记录丢失。

未知的插件数据协议版本拒绝写入并显示升级提示。缺失的非核心字段标记未知。导入消息包含成功角色数、新增事件数、重复跳过数和待核对数；详细路径和来源仅在导入诊断页出现。

## 8. 开发顺序与验收场景

先验证国服客户端的数据采集能力与四来源身份归属，再实现本地数据库和导入管线，然后完成目标及统一界面，最后处理归档、备份和打包。不能先宣称完整自动同步，再补采集依据。

关键验收场景：

- 四个来源的数据导入后出现在统一角色列表，页面没有子账号分组或标签。
- 同一角色及同一事件重复导入不会重复出现，旧快照不会覆盖新状态。
- 只计划英雄 BOSS A，击杀 BOSS A、BOSS B 后，计划页面仍只显示英雄 BOSS A。
- 添加计划前已经采集到的当周 BOSS，可以在添加计划后正确匹配。
- 英雄与史诗的同名 BOSS 独立匹配；普通拾取资格与击杀状态独立展示。
- 计划之外的活动能计入游戏实际宝库进度；上一周领奖不改变本周目标。
- 用币意向不扣余额；实际消耗独立记录并能查看关联奖励。
- 首次导入只有余额，不伪造历史流水；无法归属的币变化不会绑定随机 BOSS。
- 删除计划后对应流水仍存在；复制上周计划不复制完成事实。
- 新周未采集角色显示待同步；余额不会随周切换清零。
- 文件暂时不可读、被截断或版本不兼容时，保留最后成功数据。
- 备份恢复可以找回角色备注、计划、历史、流水和数据来源映射。

验收在实现阶段针对身份合并、去重、周切换和计划过滤做业务测试，并使用国服真实插件样本核对同步结果。此文档阶段只进行规格一致性审阅。
